### React がレガシーモードをすべての配布物で無効化する

【React】React のフィーチャーフラグで、レガシーモード（`ReactDOM.render` 系の同期的な旧挙動）が、最後に残っていた React Native の OSS レンダラーでも無効になりました。PR 本文は「これでレガシーモードは完全にオフになり、削除できる」と書いています。

**何が変わる**
- `packages/shared/forks/ReactFeatureFlags.native-oss.js` の1行の変更（1 file, +1/-1）。フラグを切るだけで、削除そのものは次の作業
- RN 用の react-test-renderer は、Web と同じく concurrent が既定になる

**なぜ変えた**
- RN は New Architecture が既定になっており、アプリ側のコードに破壊的変更はないと PR は述べている。コードサイズも小さくなる

**何に効く・誰が困る**
- 非推奨の react-test-renderer を使い続けているアプリは、`act()` の導入か testing-library への移行が必要（PR 本文）
- ただし RN のレンダラー同期は、次の React Native リリースの破壊的変更の窓まで行われない（PR 本文）

**ここまでの経緯**
- 今回: #38364 で全環境のフラグが off に
- 以前の経緯は、この号では過去の号を検索していないため「不明」

出典: https://github.com/facebook/react/pull/38364

## 今日の深掘り

### TypeScript：戻り値の文脈型から推論するとき、ユニオンを保つ（#65617）

選んだ理由：`ok([])` のような書き方が、型引数の推論でどう壊れるかを、わずか数行のdiffで追えるためです。

**背景**
- Issue #64690。`const` 型パラメータの関数 `ok<const T>(value: T): Ok<T>` を、`Ok<string[]> | Err<string>` を返す関数の中で `ok([])` と呼ぶと、`[]` が readonly タプルに推論され、戻り値の型が合わなくなる退行（PR 本文より）

```ts
type Ok<T> = { ok: true; value: T };
type Err<E> = { ok: false; value: E };
declare function ok<const T>(value: T): Ok<T>;
export function f(): Ok<string[]> | Err<string> { return ok([]); }
```
（`tsc/testdata/tests/cases/compiler/contextualReturnTypeInferenceUnions.ts`、コミット b96365b4ed）

**変更点**（`tsc/internal/checker/checker.go`、2行）

```go
// inferTypeArguments
- c.inferTypes(returnContext.inferences, returnSourceType, inferenceTargetType, InferencePriorityNone, false)
+ c.inferTypes(returnContext.inferences, returnSourceType, inferenceTargetType, InferencePriorityReturnType, false)
// instantiateContextualType
- if t.flags&TypeFlagsAnyOrUnknown == 0 {
+ if t.flags&(TypeFlagsAnyOrUnknown|TypeFlagsNever) == 0 {
```

- 1つ目：戻り値型からの推論に `InferencePriorityReturnType` という優先度を付ける。コミットのメッセージ（"Produce union types when instantiating generic contextual types"）と合わせると、複数の候補を1つに絞らず、ユニオンとして文脈型に残す方向の変更と読める。優先度の効き方そのものはソースの該当箇所を深くは追っておらず、**推測**を含む
- 2つ目：`never` になった文脈型を、`any`/`unknown` と同じく「使わない」側に回す

**周辺**
- `inferTypeArguments` が、呼び出しの外側の文脈（戻り値の期待型）から `returnMapper` を作り、`instantiateContextualType` が引数式の文脈型を決めるときにそれを使う、という二段構え
- 期待型を狭く決めすぎると `[]` が readonly タプルに倒れる、というのが今回の症状

**設計思想**
- PR によれば、狙いは「文脈型にできるだけ情報を残す」こと。DT（DefinitelyTyped）の回帰はなく、性能もほぼ中立、Jake Bailey が承認し Anders Hejlsberg がマージ（PR ページの要約）

出典: https://github.com/microsoft/TypeScript/pull/65617

### Next.js：fast `setImmediate` が `nextTick` 由来のマイクロタスクを追い越す不具合（#102237）

選んだ理由：Node のイベントループの順序（nextTick → microtask → immediate）を、プリレンダー判定のためにどう再現しているかが分かるためです。

**背景**
- Issue #102141。microtask → nextTick → microtask → immediate という連鎖だけが非同期処理のページで、「uncached or runtime data」でプリレンダーに失敗するか、部分プリレンダーになる

**原因**
- チェックが走る時点では、先に積まれた tick はすでに実行されてカウンタ `pendingNextTicks` が減っているが、その tick が積んだ microtask は tick キューが空になるまで走らない。そのためカウンタだけを見ると「何も待っていない」ように見える

**修正**
- チェックを積む直前に `pendingNextTicks > 0` をスナップショットし、スナップショットか現在のカウンタのどちらかが 0 でなければ再試行する。新しいモジュール状態は増やさず、`process.nextTick` のラッパーも変えない
- `fast-set-immediate.external.test.ts` に、この順序のテストが追加された

**設計思想**
- 「カウンタが0」と「何も保留中ではない」は別、という並行処理の定番。順序保証をテストで固定している

出典: https://github.com/vercel/next.js/pull/102237 （コミット e4e1bc9ba3）

### whatwg/html

#### `readonly` の入力要素は、型を問わず制約検証の対象外になる

【HTML】`<input readonly>` は制約検証から除外される（barred from constraint validation）と決まっていましたが、`readonly` が適用されない type（`checkbox` など）でも除外になるよう、文面が明確になりました。「適用されない属性は無視する」という一般規則に「要件が明示的に別と言わない限り」を足し、readonly の項に「適用されない場合でも同じ」と加えています。
なぜ変えたか：Issue #8133 の指摘への対応。実装と仕様の食い違いを埋めるものと思われるが、議論の中身は読んでいない（**推測**）。
