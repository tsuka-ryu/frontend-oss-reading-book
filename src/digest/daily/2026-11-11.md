## トップニュース

### Vite の仮想モジュールのID未エスケープが、dev server のRCEになる

【脆弱性】Vite の `__vite-browser-external:` と `__vite-optional-peer-dep:` という仮想モジュールが、URL由来の文字列をエスケープせずJSコードに埋め込んでいた。これを突くと、`--host` で公開されたdev serverで任意コードが実行できる。詳細は「脆弱性」の節。

**何が変わる**

- 修正は `packages/vite/src/node/plugins/resolve.ts` と `optimizer/esbuildDepPlugin.ts`。埋め込む値を `JSON.stringify` で文字列リテラルにしてから、テンプレートリテラルへは変数として渡す形に直した（[e5f23b60f](https://github.com/vitejs/vite/commit/e5f23b60f0c46a906a60986faad88a5bd7611a15)、v7.3.8 のコミット）。

**なぜ変えた**

- 仮想モジュールのIDは、リクエストURLに由来する。それをバッククォートの文字列にそのまま展開していたので、`` ` `` や `${` を含むIDでコードが抜け出せた。

**何に効く・誰が困る**

- dev serverをネットワークに出している開発者（`--host` や `server.host`）。出していなければ対象外。

**ここまでの経緯**

- 2026-10-06：`server.fs` まわりのアドバイザリが3件公開（今回の前提となる fs.allow の話）
- 2026-11-09：修正 #24043 がマージされ、8.3.7 / 8.2.5 / 8.1.7 / 7.3.8 / 6.4.6 が同日に公開
- 2026-11-10：アドバイザリ GHSA-p4f5-76q4-ffq7 が公開（Critical、CVSS 4.0 で 9.1）

出典: https://github.com/vitejs/vite/security/advisories/GHSA-p4f5-76q4-ffq7

## 今日の深掘り

### 「エスケープ漏れ」はどこで起きたか：Vite の仮想モジュール生成を読む

選んだ理由：テンプレートリテラルで「コードを文字列として組み立てる」設計は、バンドラ全般に共通する落とし穴で、修正のdiffが小さく読みやすいため。

**背景**

- Vite は `node:fs` のようなブラウザで使えない依存を、dev中は「externalizeされた」仮想モジュールに差し替える。アクセスすると警告やエラーを出すProxyを返す仕組み。
- そのコードは文字列で生成される。ID（`__vite-browser-external:<suffix>`）はURLから来る、つまり外部入力。

**変更点**

修正前（resolve.ts、要点のみ）：

```ts
id = id.slice(browserExternalId.length + 1)
return `export default new Proxy({}, { get(_, key) {
  throw new Error(\`Module "${id}" has been externalized ...\`) } })`
```

`${id}` は生成コードの中の「テンプレートリテラルの中身」に直接入る。IDに `` `)); ...; (`` のような列を入れると、リテラルを閉じて任意のコードを書ける。

修正後：

```ts
const modulePath = JSON.stringify(id.slice(browserExternalId.length + 1))
// 生成コード側
const path = ${modulePath}
throw new Error(`Module "${path}" has been externalized ...`)
```

値を先に `JSON.stringify` でJSの文字列リテラルにし、エラーメッセージ側は生成コード内の変数 `path` を参照する。外部入力が「コード」ではなく「データ」の位置にしか来なくなる。

**周辺コード**

```mermaid
flowchart LR
  A[リクエストURL] --> B[resolveId: 仮想モジュールID]
  B --> C[load: JSコードを文字列で生成]
  C --> D[Viteがそのコードを信頼して実行・変換]
  D --> E["new Worker / import.meta.glob の値を eval"]
```

アドバイザリによると、注入されたimportで `server.fs` の許可リスト外のファイルが読め、さらに `eval` を使う箇所からサーバー側のコード実行に届く。`exports` や `require` などのグローバルをブロックする方式は、セキュリティ境界にならないと明記されている。

Vite 8 では同じ処理が Rolldown 側のバイナリにあり、修正は Rolldown の更新（8.3.7 / 8.2.5 は Rolldown 1.2.17、8.1.7 は 1.1.7）に依存している（アドバイザリの記述。8.x側の差分は今回読んでいない）。

**設計思想**

- 「自分で生成したコードは安全」という前提が崩れる例。生成コードに入る値はすべて外部入力として扱い、コード生成の時点でリテラル化する。
- dev serverは本来ローカル専用の前提で、`--host` で公開した時点で信頼境界が変わる。

出典: https://github.com/vitejs/vite/commit/e5f23b60f0c46a906a60986faad88a5bd7611a15

## 脆弱性

### Vite：`__vite-browser-external` 仮想モジュール経由のRCE（Critical）

【脆弱性】GHSA-p4f5-76q4-ffq7、CVEなし、CVSS 4.0で9.1、CWE-116。2026-11-10公開。

**影響**

- vite：>=8.3.0 <=8.3.6、>=8.2.0 <=8.2.4、>=8.0.0 <=8.1.6、>=7.0.0 <=7.3.7、>=4.0.0 <=6.4.5
- 修正版：8.3.7、8.2.5、8.1.7、7.3.8、6.4.6。`vite-plus` は <=1.5.0 が対象で、1.5.1 で修正
- 成立条件：`--host` または `server.host` でdev serverをネットワークに公開している場合のみ

**攻撃原理**

- 仮想モジュール `__vite-browser-external:<suffix>` と `__vite-optional-peer-dep:<suffix>` が、URL由来のIDを未エスケープで生成コードに埋め込む
- 注入したimportで `server.fs` の許可リスト外のファイルを読める
- `new Worker` と `import.meta.glob` の値を `eval` する箇所があり、グローバルのブロックリストは回避できるため、サーバー側のコード実行に至る

**修正コミット**

- [e5f23b60f](https://github.com/vitejs/vite/commit/e5f23b60f0c46a906a60986faad88a5bd7611a15)（#24043）：埋め込みを `JSON.stringify` でリテラル化。詳細は深掘りの節。v8 の本体側は Rolldown の更新で対応（アドバイザリの記述）

**同種のパターン**

- 生成コードへの外部入力の未エスケープ展開（コードインジェクション）。2026-10-06 の Vite の `server.fs` 系も、同じdev server公開が前提だった。

出典: https://github.com/vitejs/vite/security/advisories/GHSA-p4f5-76q4-ffq7
