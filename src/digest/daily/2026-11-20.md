## トップニュース

### Next.js の `next start` の手前に、Go 製の「前段サーバー」が入る

【Next.js】`__NEXT_EXPERIMENTAL_FRONT_SERVER=1` を付けると、Go の小さなプログラムが公開ポートを受け持ち、全リクエストを背後の Node サーバーへそのまま転送します（#101695）。翌日には名前が Switchyard に変わりました（#102035）。

**何が変わる**

```text
client ──► Go（公開ポート :3000） ──► Node 127.0.0.1:<OS が選ぶ>
```

- Go 側は `httputil.ReverseProxy` で中継するだけで、ルーティングの判断はしない（PR 本文）
- Node は私的なポートで先に起動し、Go を子プロセスとして起動する。「準備完了」の行（`NEXT_FRONT_READY <port>`）を待ってから `Local:` / `Ready` を表示する
- タイムアウトは Node の値（keep-alive、headers、request）を引数で Go に渡して揃える。Go 側に既定値は持たせない
- 変数を付けなければ何も変わらない。`next` はバイナリを配布せず、`NEXT_BUILD_FRONT_SERVER=1` でビルドしたときだけ手元用に作る（Go 1.24 以上が必要）

**なぜ変えた**

PR 本文によれば、`next start` を Vercel のプロキシの形に近づける「第1段階」です。Node から Go へ、仕事を少しずつ移すための入口を先に作る狙いです。次の段階の中身は PR 本文に書かれておらず、不明です。

**何に効く・誰が困る**

- 意図的な差が2つ明記されている。HTTP/1 の理由句（reason phrase）が Go の標準の文言になり、`res.statusMessage` の独自値は残らない（例：`413 Payload Too Large` が `413 Request Entity Too Large` に）。壊れた URL（`/%zz` など）は Node に届く前に Go が 400 を返す
- ステータスコードと本文は変わらない。実験的で、既定ではオフ
- Windows は非対応（終了コード 1）

**ここまでの経緯**

- 2026-11-19（現地）：#101695 がマージ（Stage 1）
- 2026-11-19（現地）：#102035 で「front server」を Switchyard に改名。環境変数は `__NEXT_EXPERIMENTAL_SWITCHYARD`、バイナリは `switchyard-<os>-<arch>` に。クライアントのソケット情報とリクエストヘッダーの上限も保つようにした

出典: https://github.com/vercel/next.js/pull/101695 / https://github.com/vercel/next.js/pull/102035

## 今日の深掘り

### 投機的パースを巻き戻すとき、コメントも巻き戻す（oxc `#29847`）

読むのは、「パーサーの巻き戻し」が持つ状態の範囲がよく分かる修正だからです。コミットは `24a1aaf25`（`crates/oxc_parser/src/cursor.rs` ほか）。コミットメッセージ（PR 本文）を根拠にしています。ここではソースの全体は読めておらず、diff の冒頭だけを読みました。

**背景**

TSX では、まずコードとして読み、だめなら JSX テキストとして読み直す、という投機的パースがあります。`x = y ? (z) : <div>(// c)</div>;` の `(// c)` は、最初は「括弧＋行コメント」と字句解析されます。読み直しで JSX テキストになっても、そのコメントは `Program::comments` に残っていました。位置が JSX テキストの中なので、oxfmt が範囲外のスライスでパニックします（Fixes #29836）。

**変更点**

- レキサーのチェックポイントに、コメントと「不規則な空白」の個数を保存する。巻き戻しで、その個数まで切り詰める
- 前のトークンも復元する。これがないと `async // c\nfunction f() {}` のコメントが `async` ではなく `function` に付いてしまう
- 例外として `rewind_keeping_trivia` を新設。トップレベル `await` の再パースは、全体を読み終えたあとに一部の文だけ巻き戻して読み直すので、後続のコメントは捨ててはいけない

```rust
// crates/oxc_parser/src/cursor.rs (24a1aaf25)
pub(crate) fn rewind_keeping_trivia(&mut self, mut checkpoint: ParserCheckpoint<'a>) {
    self.lexer.keep_trivia(&mut checkpoint.lexer);
    self.rewind(checkpoint);
}
```

**周辺コード**

11-15 の号で扱った「先読みと投機的パースを減らす」流れの延長にあります。投機的パースを減らしても、残るものの巻き戻しは正確でなければならない、という話です。

**設計思想**

トークン列は巻き戻せても、パーサーが副産物として溜めるもの（コメント、空白）は別の置き場にあります。巻き戻しの対象を「どこまで」と決めるのが、投機的パースの正しさの要です。出典: https://github.com/oxc-project/oxc/pull/29847

### oxc-project/oxc

注目：

#### TSX の `<T extends U` を TypeScript と同じく型パラメーターの開始とみなす

【oxc】TSX で `<T extends U>` を、これまで oxc は JSX 要素の可能性にも寛容に読み直していました。TypeScript は `extends` の次が `=`、`>`、`/` 以外なら、ジェネリックアロー関数の開始とみなし、失敗すれば構文エラーにします。それに合わせ、構文エラーになる入力が出ました（#29910、#29909 は JSX ファイルで `<` を決してジェネリックアロー関数の開始と読まない修正）。
なぜ変えたか：TypeScript との挙動の差（Fixes #29899）をなくすため。
出典: https://github.com/oxc-project/oxc/pull/29910

#### 標準デコレーター用のランタイムヘルパーが入る

【oxc】`@oxc-project/runtime` に `decorateElement`、`decoratorStart`、`runInitializers`、`decoratorMetadata`、`setClassName` などが追加（#29447）。クラスデコレーターが Proxy を返しても、メタデータは `Object.defineProperty` で自身のデータプロパティとして付ける、という設計です。
なぜ変えたか：標準デコレーターの低レベル化に、適用・メタデータ共有・初期化子の実行のヘルパーが必要だったため。
出典: https://github.com/oxc-project/oxc/pull/29447
