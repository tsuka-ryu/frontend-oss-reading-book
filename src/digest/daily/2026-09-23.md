## トップニュース

next/og（`ImageResponse`）に、生成画像のクエリパラメータなどを細工するとサーバー側でコードを実行できる、深刻度Critical（CVSS 9.5）の脆弱性が見つかった。同日中に修正版v16.3.6・v15.5.26が緊急リリースされた。

**何が変わる**：SVGの属性値・スタイル文字列を組み立てる箇所にXMLエスケープを追加した。要素名・属性名の妥当性検証、SVGをdata URLへ埋め込む際の`&`エンコードもあわせて追加している。

**なぜ変えた**：テキストノードの中身は元から`escape_html`でエスケープされていたが、`style`・`filter`・`clip-path`のようにテンプレートリテラルで組み立てる属性値はエスケープを通っていなかった。

```js
// 修正前（@vercel/og の旧バンドルより）
style: b.filter ? `filter:${b.filter}` : void 0,
// b.filter が攻撃者制御なら、ここでSVG属性の外へエスケープできる
```

**何に効く・誰が困る**：`runtime: 'nodejs'`を指定した`ImageResponse`で、ユーザー入力をSVGの内容・属性・スタイルへそのまま渡しているアプリ。Edge実装は影響を受けない。影響バージョンはnpm `next` 16.2.0以上16.3.6未満（CVE-2026-94545）。

**ここまでの経緯**：このダイジェストは今回が初回のため、報告から修正までの経緯は追えていない。確認できた事実だけを書く。

## 今日の深掘り

### next/ogのSVGシリアライズは、なぜ属性値のエスケープを見落としていたか

選んだ理由：本日最大のニュースであり、「テキストノードは注目されるのでエスケープされるが、属性値は見落とされやすい」というエスケープ漏れの典型パターンとして教材価値が高い。

背景：`next/og`はSatoriというライブラリをベースに、Reactライクな要素ツリーをSVGへ変換してPNG画像を生成する。SVG化の際、テキストノードの中身は早くから`escape_html`（`"`,`'`,`&`,`<`,`>`をエンティティに置換する小さな関数）を通していたが、`style`・`filter`・`clip-path`・`stroke`のような属性値は文字列テンプレートで直接組み立てられており、エスケープを通っていなかった。

変更点：修正コミット（PR #99061）は`@vercel/og`のバンドル済みコード自体を、パッチの当たった新しいSatori（0.29.0ベース、0.33.5まで許容）でビルドし直す形で入っている。差分を見ると、要素を組み立てる関数（`M`/`C`のような小さなヘルパー）の呼び出し側で、テキストノードだけでなく属性値の組み立てもエスケープ経由に変わっている。

```js
// 修正後（バンドル差分より）
let S2 = { ..., style: b.filter ? `filter:${b.filter}` : void 0, ... },
    T = C("text", { ...S2, fill: b.color }, (0, import_escape_html2.default)(t)) + (m2 || "");
```

周辺コード：SVGを組み立てる関数群は、Reactの`createElement`に似た形でノードツリーを受け取り、要素名・属性・子要素を文字列として連結してSVGソースを作る。エスケープをテキストノードの出力箇所だけに置くと、属性値を組み立てる別の場所までは防げない。今回の修正は、SVG文字列に値を書き込む出入り口（シリアライザの境界）を1箇所に絞り、そこで一律にエスケープする設計に寄せている。

この変更から分かる設計思想：エスケープは「値を使う場所ごと」に書くと漏れが起きやすい。出力の境界に寄せて一律に処理する方が、新しい属性が増えても安全性が保たれる。

出典: https://github.com/vercel/next.js/pull/99061 、アドバイザリ: https://github.com/vercel/next.js/security/advisories/GHSA-vcvr-r3jv-pc5j

### oxcレキサーが、曖昧トークンの判定を「3段階の状態機械」に書き換えた

選んだ理由：`/`が除算か正規表現か、`<`が比較演算子かJSXの開始かといった「前後の文脈を見ないと決められないトークン」の判定は、多くの言語処理系が抱える設計課題で、パーサー/レキサーの内部設計を学ぶ題材として適している。

背景：JavaScriptの字句解析は、1文字先読みだけでは決められないトークンを含む。`x / y`の`/`は除算だが、`function*(){ yield /re/ }`の`/`は正規表現になりうる。従来のoxcの実装は、こうした曖昧トークンをその場その場のロジックで処理していたが、キーワードの綴りをそのまま使ったプロパティ名やクラス継承式、ASI（自動セミコロン挿入）が絡むケースで誤判定するバグに加え、`yield`を含むgeneratorの中で除算が続くようなファイルでは判定コストが二次関数的に増えて遅くなる問題があった。

変更点：PR #26919は、曖昧トークンの判定を3段階の状態機械に整理した。コミットメッセージから引用する。

```
Level 1 - O(1) look behind; If it's context-independent we resolve the
ambiguity from the previous token.
Level 2 - Finite backward check, context-independent resolves some cases
that are rare in user-code
Level 3 - Full state-machine that runs essentially the JS lexical rules
to resolve the grammar; This is for fully context-dependent ambiguity
and almost never appears in real user-authored code.
```

多くのコードは直前のトークンだけで判定できるLevel 1（O(1)）で片付き、レアなケースだけがLevel 2の有限の後方チェック、さらに稀なケースだけがLevel 3のフル状態機械（JSの字句規則をなぞる）に到達する。「発生したときだけ払う（pay-when-occurs）」設計により、最悪計算量も従来の二次関数的な悪化ではなく、ファイル全体をトークン単位で1回なめるO(N)に抑えている。判定対象そのものは`crates/oxc_lexer/src/pipeline/disambiguate/operator/mod.rs`のドキュメントコメントに残っている。

```rust
//! Is a position directly after a complete value?
//!
//! [`not_operator_position`] answers this for `carve`, to tell a regex from division,
//! and a JSX element from less-than. Its doc comment explains the question in detail.
```

周辺コード：`carve`と呼ばれるモジュールが字句解析の初期段階でトークン列を粗く切り出し、この曖昧トークン判定（disambiguate）はその内部で呼ばれる。変更は`pipeline/carve/js.rs`、`pipeline/carve/jsx/`配下、`pipeline/disambiguate/`配下の広い範囲（47ファイル、5800行超）に及ぶ。

この変更から分かる設計思想：曖昧さの解決コストを「発生頻度に比例させる」設計は、ホットパス（大多数の単純なコード）の速度を犠牲にせず、レアケース（極端な入力を含む）の正しさも諦めないための定石である。コミットメッセージにある通りまず「correct」を優先し、保守性のためのリファクタリングは後続のPRに回すという段階的な進め方も読み取れる。

出典: https://github.com/oxc-project/oxc/pull/26919

### w3c/csswg-drafts

#### filter-effects-1にクリックジャッキング対策の制限が明文化される

【CSS】cross-originのiframeに対するSVGフィルター適用を制限し、same-originのiframeには従来通り適用を許可する規定をFilter Effects仕様に追加した。SVGフィルターでiframeの見た目を操作・隠蔽するクリックジャッキング攻撃を防ぐのが狙いで、Chromeの機能提案を仕様に落とし込んだもの。レビューでは「制限をすべてのiframeに広げるか、cross-originだけにするか」が論点になり、「same-originフレームはセキュリティ境界ではない」という理由でcross-origin限定に落ち着いた。
なぜ変えたか：SVGフィルターを使ったクリックジャッキング攻撃を仕様レベルで塞ぐため。
出典: https://github.com/w3c/csswg-drafts/pull/13846

動きなし：whatwg/dom, whatwg/fetch, whatwg/streams, whatwg/url, w3c/aria, w3c/ServiceWorker, w3c/wcag3, tc39/proposals, tc39/ecma262

#### Reactコンパイラ：エフェクト内のawait後のsetStateを許可

【TypeScript】プロジェクト参照のビルド順序を、これまでの深さ優先走査から、依存の浅いプロジェクトを先に投入する安定ソートへ変更。19,430プロジェクト規模のモノレポでは32ビルダーのうち平均13個しか稼働していなかったのが、この変更で中央値530秒→262秒とビルド時間が約2倍高速化（ピークメモリは約15%増）。
なぜ：深い依存チェーンを持つプロジェクトを先に拾うと、他のビルダーが上流の完了待ちで遊んでしまっていたため。
出典: https://github.com/microsoft/TypeScript/pull/64220

#### tsgoのfswatchで大文字小文字の取り違えを修正

【TypeScript】macOSのFSEventsは登録したパスと異なる大文字小文字でコールバックを返すことがあり、これによりファイル変更イベントが静かに落とされていた。
なぜ：大文字小文字が異なるだけでウォッチイベントが無視され、エディタでの変更検知が効かなくなる不具合を直すため。
出典: https://github.com/microsoft/TypeScript/pull/64210

#### オブジェクトの分割代入デフォルト値の扱いを配列と揃える

【TypeScript】これまでオブジェクトの分割代入パターンは、自身に初期化子を持つ要素だけを「欠けている要素」として補完していたが、配列パターンはすべての欠けている要素を補完していた。この非対称を解消。
なぜ：同等の意味を持つオブジェクト引数と配列引数で型推論結果や診断が食い違っていたため。
出典: https://github.com/microsoft/TypeScript/pull/64043

#### tsgo自作lintで「breakだけのcaseブロック」「トップレベルbreak」を禁止

【TypeScript】GoのswitchはJSと違いフォールスルーしないため、`break`だけのcaseは空のcaseと同じ情報量しかなく紛らわしいとして禁止するルールを追加。
なぜ：GoではJSと違いcaseは自動フォールスルーしないため、`break`のみのcaseは紛らわしいため。
出典: https://github.com/microsoft/TypeScript/pull/64153

#### オブジェクトプロパティ補完でクォート設定を尊重するように

## 議論ウォッチ

### CSSの`flow-start`/`flow-end`整列キーワードに、Mozilla・WebKitへのポジション照会が同時に立つ

【CSS】
- 論点：Flexbox/Grid masonryで`fill-reverse`/`track-reverse`により要素の並びが反転したとき、`align-items`/`justify-items`などの`start`/`end`を「見た目上の配置」基準にするか「論理的なflow方向」基準にするかがcsswg-drafts#14052で未解決のまま、それを解決する新キーワード`flow-start`/`flow-end`をCSS Alignに追加する案が浮上している。
- 賛否：反転後も`start`/`end`の意味を変えない立場（`align-content: start`が反転後に下端を指すのは分かりにくい）と、`flex-direction: column-reverse`＋`justify-content: flex-end`が論理方向に追従する既存挙動に合わせるべきという立場が対立している。
- 今回の進展：9月22日、MozillaとWebKitの両standards-positionsリポジトリに、この提案へのポジション照会issueがほぼ同時に立った（Mozilla #1455、WebKit #723）。執筆時点ではどちらも"Unscreened"でベンダーの正式な立場はまだ示されていない。Chromiumはすでに実装に着手している。
- 次に決まりそうなこと：MozillaとWebKitがポジションを表明し、それを受けてcsswg-drafts#14052でのCSSWGの議論が進む見通し。

出典: https://github.com/mozilla/standards-positions/issues/1455 、https://github.com/WebKit/standards-positions/issues/723 、https://github.com/w3c/csswg-drafts/issues/14052

### TC39 2026年9月会議に、無効な入力文字列のエラー種別（RangeError/TypeError）統一が議題として追加される

【TC39】
- 論点：JS標準ライブラリの各APIが無効な文字列入力を受けたときに投げる例外が`RangeError`だったり`TypeError`だったりまちまちで、どちらを使うべきかの規約がこれまで明文化されていなかった。
- 賛否：議題自体はgibson042が提出。レビューでmichaelficarraから「新しい規範的な規約の話か、個別の具体的な提案の話か」を問われ、提出者は「新しい規範的な規約を確立する」ものだとタイトルを修正した。実際の賛否は会議本番でこれから交わされる。
- 今回の進展：9月22日、2026年9月TC39総会のアジェンダにこの議題を追加するPRがマージされた。
- 次に決まりそうなこと：会議本番での議論を経て、合意できれば「規範的な慣習」としてTC39内のガイドラインに反映される見通し。議事結果はまだ公開されていない。

出典: https://github.com/tc39/agendas/pull/2163

## 脆弱性

### next/ogのImageResponse（Node実装）にSVGインジェクションによるRCE（GHSA-vcvr-r3jv-pc5j, CVE-2026-94545）

【脆弱性】

**影響するパッケージとバージョン、深刻度**：npm `next` 16.2.0以上16.3.6未満。CVSS v4スコア9.5（Critical）。修正版は16.3.6（15.x系はv15.5.26にバックポート）。

**攻撃原理**：next/ogの`ImageResponse`（Node実装）は、渡された要素ツリーをSatoriベースのシリアライザでSVG文字列に変換してPNGを生成する。テキストノードの中身は`escape_html`でエスケープされていたが、`style`・`filter`・`clip-path`などテンプレートリテラルで組み立てる属性値はエスケープされていなかった。クエリパラメータなど攻撃者が制御できる値をこれらの属性経由でSVGに渡すと、属性値の外へ抜け出して任意のSVG要素を注入できる。

**影響バージョンと成立条件**：Node実装（`runtime: 'nodejs'`）の`ImageResponse`に、サニタイズしていないユーザー入力をSVGの内容・属性・スタイルとして渡しているアプリが対象。Edge実装は影響を受けない。

**修正コミットのdiff解説**：修正PR #99061は、`@vercel/og`をパッチの当たった新しいSatori（0.29.0ベース、0.33.5まで許容）でビルドし直す形で入っている。シリアライズの出入り口（`M`/`C`のような要素組み立て関数）で、テキストノードだけでなく属性値の組み立ても`escape_html`経由に統一し、あわせて要素名・属性名の妥当性検証、SVGをdata URLへ埋め込む際の`&`エンコードも追加した。

**同種の脆弱性パターン**：テンプレートリテラルで生成した文字列を、構造化データ（HTML/SVG/XMLなど）の一部としてそのまま埋め込むと起きるインジェクションの一種。「テキストノードだけエスケープして属性値を見落とす」のは典型的な抜け漏れパターンで、HTMLのテンプレートエンジンやSSRのレンダラーでも繰り返し起きる。

出典: https://github.com/vercel/next.js/security/advisories/GHSA-vcvr-r3jv-pc5j 、修正PR: https://github.com/vercel/next.js/pull/99061
