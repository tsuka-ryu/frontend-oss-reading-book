## トップニュース

### React：`useId` が、大きなツリーで別の位置に同じIDを返すバグが直る

【React】`useId` は、ツリー上の位置を数にして、その文字列を返す。位置の数が30ビットを超えると、あふれた分を base-32 の文字列に切り出すが、そのとき先頭の `0` が落ち、別の位置が同じ文字列になっていた。

**何が変わる**

- あふれた部分の文字列を、5ビットにつき必ず1文字になるよう `padStart(numberOfOverflowBits / 5, '0')` で埋める
- サーバー側（`ReactFizzTreeContext.js`）と、ハイドレーション側（`ReactFiberTreeContext.js`）の両方に、同じ修正が入った
- 先に、バグのある挙動をそのまま固定したテストを書いてから直している。64個のIDのうち63個しか重複しない、という挙動が、64個すべて一意になった

**なぜ変えた**：IDの重複は、`aria-labelledby` のようなARIAの参照を壊す。`useId` が約束している「一意」が、深くて大きなツリーでは守られていなかった（PR本文より）。

**何に効く・誰が困る**：とても大きく、深いツリーでIDを使う画面。フォーム部品やダイアログのラベル付けでIDを使うライブラリ。

**ここまでの経緯**

- Issue #37911 で報告
- 先に出た #37912 は、`slice()` が毎回メモリを確保するため、作者が閉じて #37916 に切り替えた
- 2026-10-20：#37916 がマージ

出典: https://github.com/facebook/react/pull/37916

## 今日の深掘り

### `useId` の文字列は、ツリー上の位置を5ビットずつ区切ったものだった

選んだ理由：IDを「連番」ではなく「位置の符号化」で作る理由と、数値から文字列への変換で起きる古典的な落とし穴が、数行の差分で読めるため。

**背景**：サーバーとクライアントで、同じ要素に同じIDを付けないと、ハイドレーションが食い違う。連番だと、描画の順番が違うだけで食い違うので、Reactは「親から何番目の子か」というツリー上の位置を符号化してIDにしている。

**変更点**：あふれた部分を base-32 にするところで、`toString(32)` は先頭の0を省く。

```js
// packages/react-reconciler/src/ReactFiberTreeContext.js（コミット ab0d927f5）
const newOverflow = (baseId & newOverflowBits)
  .toString(32)
  .padStart(numberOfOverflowBits / 5, '0');
```

`numberOfOverflowBits` は5の倍数なので、1文字が5ビットに対応する。たとえば `00001` と `1` が同じ `"1"` になれば、別の位置が衝突する。幅を固定すれば、文字列の長さが位置を一意に決める。

**周辺コード**：サーバー（Fizz）が書き出したIDを、クライアントのFiberが同じ規則で再計算して照合する。そのため、2か所を同時に直す必要がある。

```mermaid
flowchart LR
  A[ツリー上の位置] --> B[30ビットを超えたらoverflowへ]
  B --> C[toString 32]
  C --> D[padStartで幅を固定]
  D --> E[useIdの文字列]
```

**設計思想**：IDの一意性を、ストアや連番ではなく、構造だけから導く。そのため、符号化は「単射」（別の入力が別の出力になる）でなければならず、可変長の文字列には幅の規則が要る。

### whatwg/html

#### Fragment scripting mode では、パーサーが挿入した `script` の force async を false にしない

【HTML】`createContextualFragment()` などで使う Fragment のスクリプトモードでは、パーサーが挿入した `script` を、パーサー挿入でないものとして扱う。今回、force async を false にする手順を、このモードの外に限った。外部スクリプトが非同期のまま実行される。
