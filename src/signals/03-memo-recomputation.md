# メモはいつ計算し直されるか

シグナルAから、メモBと、エフェクトCの両方に依存の線が伸びているとする。
CはAを直接読み、Bも読んでいる。
グラフを描くと菱形になる。
Aを書き換えたとき、Cは何回走るか。

キューに積まれた順に実行するだけなら、二回走る。
Aの変更で先にCが実行されると、Cは新しいAと、まだ再計算されていない古いBを同時に見ることになり、そこでBが再計算されるとCがもう一度走る。
この一時的な不整合は、リアクティブシステムの文献で**グリッチ**と呼ばれる古典的な問題である。
Solidでは、Cは一回しか走らず、走った時点でBは必ず新しい。

## 二種類の印

前章で見たとおり、`writeSignal` はシグナルを直接読んでいた計算に `STALE`（確実に古い）の印を付ける。
その計算がメモ、つまり自分にも読み手がいる計算だった場合は、続けて `markDownstream` が呼ばれる。

```ts
function markDownstream(node: Memo<any>) {
  for (let i = 0; i < node.observers!.length; i += 1) {
    const o = node.observers![i];
    if (!o.state) {
      o.state = PENDING;
      if (o.pure) Updates!.push(o);
      else Effects!.push(o);
      o.observers && markDownstream(o);
    }
  }
}
```

ここで付く印は `STALE` ではなく `PENDING`（古いかもしれない）である。
Bの再計算の結果が前と同じ値なら、Cの再実行は要らない。
たとえばBが「Aは偶数か」を返すメモなら、Aが2から4に変わってもBは真のままで、Bだけを読むCに変化は届かないはずである。
それはBを計算してみるまで分からないから、下流には確定の印を付けようがない。
菱形の例では、Cには両方の経路から印が届くが、`state` が空のときしかキューに積まれないため、二重には積まれない。

実行の段になると、この印の違いが挙動の違いになる。
キューの各計算は実行前に自分の `state` を確認し、`PENDING` なら `lookUpstream` で自分の依存元を辿り、`STALE` な上流を先に更新させる。
`lookUpstream` は入口で自分の印をいったん消す。
上流のBを再計算した結果が変わっていれば、メモの書き戻しは書き込み時と同じ `comparator` の関門を通って `STALE` を付け直し、変わっていなければ印は消えたままになる。
先の偶数の例なら、Cは印が消えた状態で自分の番を迎え、何もせずに終わる。

もう一つ、実行を待たずに更新が起きる経路がある。
`readSignal` の冒頭である。

```ts
export function readSignal(this: SignalState<any> | Memo<any>) {
  if (this.sources && this.state) {
    if (this.state === STALE) updateComputation(this);
    else {
      const updates = Updates;
      Updates = null;
      runUpdates(() => lookUpstream(this), false);
      Updates = updates;
    }
  }
  // ...（前々章で見た依存記録の処理が続く）
```

古い印の付いたメモは、誰かに読まれたその場で計算し直される。
つまりSolidの伝播は、書き込み時には印を配るだけで、実際の計算は消化か読み取りのときまで遅らせる。
印を押し出して配り、値は必要になったときに引き出す。
この組み合わせは**push-pullハイブリッド**と呼ばれる方式である。

## 名前が逆だった二つの関数

印を二種類にする設計は、2019年8月、v0.10.0の準備コミットまで遡れる。
当時のコードは時刻カウンタと各ノードの世代を比べるS.js系の作りで、いまの `STALE`/`PENDING` と `ExecCount` の形になったのは2020年3月のリファクタ以降である。

履歴には設計の難しさを示す逸話も残っている。
下流に印を配る関数は長らく `markUpstream` という名前で、上流を確かめる関数は `lookDownstream` だった。
つまり上流と下流の名前が逆に付いたまま数年使われており、2022年4月のPR #921でようやく現在の名前に入れ替えられた。
伝播の向きは、実装者自身が取り違えるほど直感に反しやすい。

グリッチを防ぐ仕掛けをもう一段支えているのが、実行前に毎回依存を張り替える機構である。
古い依存の線が残っていたら、印はそもそも正しい相手に届かない。
その張り替えを次章で見る。
