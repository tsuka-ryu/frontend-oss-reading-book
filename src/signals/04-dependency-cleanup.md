# 依存の付け替えはどう行われるか

`show() ? a() : b()` を本体に持つ計算を考える。
`show` が真の間、この計算は `show` と `a` に依存している。
`show` が偽に変わって再実行されると、今度は `b` を読み、`a` は読まない。
このとき `a` への購読は残るのか。
残るなら、`a` を変えるたびに、もう結果に関係しない再計算が走り続けることになる。

前回と今回の依存を比べて、増えた分を購読し、減った分を解除する。
差分を取るこの方式が素朴には思い浮かぶが、Solidはそうしていない。
再実行のたびに、依存を全部捨てて、ゼロから張り直す。

## 毎回すべて捨てる

計算を再実行する `updateComputation` は、本体の関数を呼ぶ前に必ず `cleanNode` を呼ぶ。
その中心が、自分の `sources`（依存元の一覧）を空にしながら、各依存元の `observers` から自分を抜いていくループである。

```ts
while (node.sources!.length) {
  const source = node.sources!.pop()!,
    index = node.sourceSlots!.pop()!,
    obs = source.observers;
  if (obs && obs.length) {
    const n = obs.pop()!,
      s = source.observerSlots!.pop()!;
    if (index < obs.length) {
      n.sourceSlots![s] = index;
      obs[index] = n;
      source.observerSlots![index] = s;
    }
  }
}
```

配列から要素を消すのに、探索がどこにもない点が本質である。
第1章の `readSignal` は、購読を張るときに「相手の配列の中で自分が何番目か」を `sourceSlots` と `observerSlots` に控えていた。
解除では、その番号で消す位置が即座に分かる。
消し方は、配列の末尾要素を抜いた穴に移す入れ替え方式で、移された要素が控えている番号も同時に書き直す。
一件あたり定数時間、`indexOf` も `splice` も使わない。

まっさらにした状態で本体を実行すると、今回実際に読まれたシグナルだけが `readSignal` 経由で購読し直される。
`show` が偽の回には `a` は読まれないから、`a` への購読は自然に消えている。
条件分岐に追従する動的な依存は、特別な機能ではなく、「毎回捨てて張り直す」ことの帰結である。
なお `cleanNode` は依存の解除だけでなく、その計算が実行中に作った子計算の破棄と、`onCleanup` で登録された後始末の実行も担っており、破棄の単位としても使われる。

張り直しのコストが毎回かかることは、この設計の代価である。
`readSignal` 側の重複チェックも、`observers` の末尾が自分かどうかを見るだけの簡素なもので、同じシグナルを連続で読む典型例だけを弾く。
Setによる厳密な集合管理を避けて配列とインデックスで通しているのは、購読の張り替えが毎フレーム級の頻度で起きる前提の割り切りだと思われる（明示的な記述は見つからなかった）。

## 番号方式はS.jsからの継承

位置番号で購読を消す仕掛けは、Solidが自前実装に切り替える前に使っていたS.jsに既にあった。
S.jsでは購読情報は `Log` という構造体に包まれ、観測者が一人だけの場合を特別扱いするフィールドと、複数用の配列・番号の対を持っていた。
2020年3月のリファクタ（v0.17.0）は、この `Log` の包みと単一観測者の特別扱いを廃止し、`observers` と `observerSlots` の平坦な配列をシグナル本体に直接持たせた。
前章までで見た形は、S.jsの発明を、コードサイズを削る方向に単純化した結果である。

依存の張り替えまでで、グラフの形を保つ仕組みは一通り揃った。
残るのは順序の問題、つまり印の付いた計算たちをどの順で走らせるかで、これを最終章で追う。
