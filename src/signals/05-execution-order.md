# エフェクトはいつ、どの順で走るか

一回の書き込みで、印の付いた計算が複数キューに並んだとする。
その中には、値を派生させるメモもあれば、DOMに書き込むエフェクトもあり、あるエフェクトの内側で作られた別の計算もある。
これらを積まれた順に走らせてよいのか。
たとえば、親にあたる計算が作り直される予定なのに、先に子を走らせたら、その仕事は直後に捨てられる。

Solidはこれを、キューの分離と、実行直前の親確認という二つの仕掛けで解いている。

## 三層に分かれた実行

キューが `Updates`（純粋な計算）と `Effects` の二本に分かれ、`Updates` が先に流れることは第2章で見た。
`Effects` の中にも順序がある。

```ts
function runUserEffects(queue: Computation<any>[]) {
  let i, userLength = 0;
  for (i = 0; i < queue.length; i++) {
    const e = queue[i];
    if (!e.user) runTop(e);
    else queue[userLength++] = e;
  }
  // ...（SSRハイドレーション時の分岐を省略）
  for (i = 0; i < userLength; i++) runTop(queue[i]);
}
```

一巡目で `user` の印がないものだけを走らせ、`user` 付きは配列の前方に詰め直して二巡目で走らせる。
`user` が付くのは開発者が `createEffect` で書いたエフェクトで、付かないのはレンダラが内部で使うレンダーエフェクトである。
なおこの二巡の関数は最初から使われるわけではない。
`Effects` を流す関数は単純な一巡のループを指す変数として持たれており、`createEffect` が初めて呼ばれた時点で `runUserEffects` に差し替えられる。
開発者のエフェクトを一つも持たないプログラムは、二巡ぶんの選別を通らない。
つまり全体は、メモなどの純粋な計算、DOMを組み立てるレンダーエフェクト、開発者のエフェクト、の三層の順で流れる。
開発者のエフェクトが走る時点では、DOMは組み立て終わっている。

この三層は最初からあったわけではない。
v0.20（2020年9月）のCHANGELOGには「Re-scheduling Reactivity」という節があり、このリリースで `createEffect` はレンダリング後へ遅延された。
同時に、遅延されては困る用途、つまり派生データを別のシグナルへ書き戻すような処理のために、遅延されない `createComputed` が分離された。
タイミングを前提にしていた旧APIが三つ、この変更で削除されている。

## 走る前に祖先を確かめる

キューの各計算を実際に走らせる `runTop` は、対象をすぐには実行しない。

```ts
const ancestors = [node];
while (
  (node = node.owner as Computation<any>) &&
  (!node.updatedAt || node.updatedAt < ExecCount)
) {
  if (node.state) ancestors.push(node);
}
for (let i = ancestors.length - 1; i >= 0; i--) {
  node = ancestors[i];
  // ...（STALEなら更新、PENDINGなら上流を確認する分岐を省略）
}
```

Transitionに関わる分岐も抜粋からは省いている。
ここで初めて**所有者**（owner）が出てくる。
すべての計算は、自分がどの計算の実行中に作られたかを `owner` として覚えており、全体は木になっている。
第4章で見たとおり、計算が再実行されると子計算は `cleanNode` で破棄されるから、「親が古い」は「自分がもうすぐ消されるかもしれない」を意味する。
`runTop` は owner の鎖を根の方向へ遡り、印の付いた祖先を集めて、外側から順に処理する。
祖先の更新で自分が破棄されれば、自分の番が来ても印は消えていて何も起きない。
各計算が持つ `updatedAt` と、更新サイクルごとに増える通し番号 `ExecCount` の比較が、同じサイクルで二度走ることを防いでいる。

外側から順に、という現在の形は2021年7月のコミット「better topological sort」で入った。
それ以前の `runTop` は、いちばん外側の古い祖先を一つ選んで実行を任せる作りで、途中に `PENDING` の祖先が挟まるケースの扱いが単純でなかった。
祖先を配列に集めて順に確かめる方式への書き換えは、正しさの修正として履歴に残っている。

これでシグナルのパートは終わりである。
書き込みは印を配るだけ、計算は読まれるか消化されるまで遅れ、依存は毎回張り直される。
「変更に印を付けて、必要になったときに確かめ直す」という無効化の設計は、このパートだけの話ではなく、後のパートで読むHMRやコンパイラのクエリシステムにも別の形で現れる。
