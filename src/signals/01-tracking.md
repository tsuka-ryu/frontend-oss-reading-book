# 読んだら覚えるシグナルを作る

> 考えることのない事物にとって、その esse（存在すること）は percipi（知覚されること）である。
>
> ——George Berkeley『人知原理論』第1部第3節（1710年、拙訳）

> 読んだ版：solidjs/solid `b25c557`（2026-09-04、solid-js 1.9.15）の `packages/solid/src/reactive/signal.ts`
>
> この章のミニ実装：`code/signals/01-tracking/`（`node --test "code/signals/01-tracking/*.test.ts"`）

次の3行を見てほしい。

```ts
const [count, setCount] = createSignal(0);
createEffect(() => console.log(count()));
setCount(1); // 1 が表示される
```

`createEffect` に渡した関数は、`count` に依存しているとはどこにも書いていない。
それなのに、`setCount` を呼ぶとこの関数はもう一度走る。

Reactの `useEffect` は、同じことをするのに依存配列を人間に書かせる。
書き忘れを見つけるためのlintルールまで用意されている。
Solidはその配列を要求しない。
では、誰が代わりに書いているのか。

この章では、その「誰か」を20行ほどで作る。
作ってみると、正体はグローバル変数が一つである。

## 用語を三つだけ

**シグナル**は、値を一つ持ち、読み取り関数と書き込み関数の組として使うものである。
**エフェクト**は、関数を一つ持ち、その関数が読んだシグナルに書き込みがあると関数を実行し直すものである。
Solidの内部では、エフェクトのように再実行される側を**計算**（Computation）と呼ぶ。

お手本はSolidのリアクティブコアで、`signal.ts` という約1,800行のファイル一つに収まっている。
関数名と変数名は、あとで比べやすいようにこのファイルに合わせる。

## 一歩目：ただの変数

まず、何も考えずに書く。

```ts
export function createSignal<T>(value: T) {
  const read = () => value;
  const write = (v: T) => { value = v; };
  return [read, write] as const;
}

export function createEffect(fn: () => void) {
  fn();
}
```

冒頭の3行を流すと、`0` が一度表示されて終わる。
`setCount(1)` は値を書き換えるが、誰にも知らせない。
これはシグナルではなく、getterとsetterに大げさな名前を付けただけのものである。

足りないのは、書き込んだときに「誰に知らせればよいか」の名簿である。
名簿は書き込みの時点で必要になるが、作れるのは読み取りの時点しかない。
エフェクトが何を読むかは、関数を実行してみるまで分からないからだ（`if` の分岐で読むものが変わることもある）。

## 二歩目：いま誰が読んでいるか

読み取り関数の中から「いま自分を読んでいるのは誰か」が分かれば、そこで名簿に書ける。
関数の呼び出し元を知る正攻法はJavaScriptにない。
そこで、実行する側が自分をグローバル変数に置いておく。
Solidと同じく、この変数を `Listener` と呼ぶ。

```ts
let Listener: Computation | null = null;

function readSignal<T>(s: SignalState<T>): T {
  if (Listener) s.observers.add(Listener);
  return s.value;
}

function writeSignal<T>(s: SignalState<T>, value: T) {
  s.value = value;
  for (const o of [...s.observers]) runComputation(o);
}
```

`createSignal` は、値と購読者の集合 `observers` を持つ `SignalState` を作り、読み書きをこの二つの関数に渡すだけになる。
`readSignal` の1行目が、この章の仕組みのすべてである。
`Listener` が空でなければ、それを名簿に足す。
`writeSignal` は名簿の全員を実行し直す（名簿を配列に複製してから回すのは、実行中に新しく加わった購読者を同じループで拾わないためだ）。

設計の教科書が最初に戒めるものの一つがグローバルな可変状態である。
それが、リアクティブの心臓部に座っている。

エフェクトの側は、自分を `Listener` に置いてから関数を実行し、終わったら片付ける。

```ts
function runComputation(node: Computation) {
  Listener = node;
  node.fn();
  Listener = null;
}
```

これで冒頭の3行は動く。
`1` が表示される。

## 三歩目：入れ子にすると外側が耳を塞ぐ

エフェクトの中で、別のエフェクトを作ってみる。
UIを部品に分ければ、すぐにこうなる。

```ts
createEffect(() => {
  createEffect(() => b());
  console.log("外側:", a());
});
setA("a1");
```

実行すると、`外側: a0` が一度出るだけで、`setA("a1")` には何の反応もない。

内側のエフェクトが終わった時点で、`Listener` が `null` に戻されたからである。
そのあと外側が `a()` を読んでも、読み手はいないことになっている。
外側のエフェクトは実行中なのに、`Listener` の上では存在しない。

直し方は2行で済む。
`null` に戻すのではなく、直前の値に戻す。

```ts
function runComputation(node: Computation) {
  const listener = Listener;
  Listener = node;
  try {
    node.fn();
  } finally {
    Listener = listener;
  }
}
```

`Listener` は一つの変数だが、使われ方はスタックになった。
`finally` は、関数が例外を投げても `Listener` が残らないようにするためのものである。
これを忘れると、例外を投げたエフェクトが、以後のすべての読み取りを自分のものとして記録し続ける。

## 四歩目：同じものを1000回読む

最後に、意地の悪い入力を試す。

```ts
createEffect(() => {
  for (let i = 0; i < 1000; i++) v();
});
setV(1);
```

名簿が配列なら、同じエフェクトが1000回登録され、1回の書き込みで1000回走る。
ミニ実装では `observers` を `Set` にしてあるので、この問題は最初から起きない。
何もしていないのに正しい。
これは覚えておいてほしい。
あとで、本物がこの1行ぶんの正しさに何年かけたかを見る。

## 確かめる

テストは6つある。
冒頭の3行が動くこと、エフェクトの外での読み取りは記録されないこと、入れ子のあとでも外側の読み取りが外側に記録されること（三歩目）、1000回読んでも1回しか走らないこと（四歩目）を確かめている。
残りの2つは、このミニ実装の欠点をそのとおりに確かめるもので、最後の節で扱う。

## Solidの readSignal と並べる

Solidで同じ役目を持つ関数も `readSignal` という。
依存を記録する部分だけを抜き出す。

```ts
if (Listener) {
  const observers = this.observers;
  if (!observers ||
      observers[observers.length - 1] !== Listener) {
    const sSlot = observers ? observers.length : 0;
    // ...（初回の配列作成を省略）
    Listener.sources.push(this);
    Listener.sourceSlots.push(sSlot);
    // ...（初回の配列作成を省略）
    observers.push(Listener);
    this.observerSlots.push(
      Listener.sources.length - 1);
  }
}
```

省略したのは、配列がまだ `null` のときに新しく作る分岐である。
`Listener` を見て名簿に書くという骨格は、二歩目のミニ実装と同じだ。

違いは名簿の持ち方にある。

| | ミニ実装 | Solid |
| --- | --- | --- |
| 実行中の計算 | `Listener` | `Listener` |
| シグナル→計算 | `observers`（Set） | `observers`（配列） |
| 計算→シグナル | なし | `sources`（配列） |
| 相手側の位置 | なし | `observerSlots`、`sourceSlots` |
| 重複の防ぎ方 | Setが勝手に防ぐ | 配列の末尾だけを比べる |

Solidは逆向きの名簿 `sources`（この計算が読んだシグナルの一覧）も持つ。
計算を実行し直す前に、前回の依存を外すためのものである（ミニ実装では3章で足し、4章で使う）。
`observerSlots` と `sourceSlots` は、相手側の配列の中で自分が何番目にいるかを覚えておく配列で、依存を外すときに相手の配列を先頭から探さずに済む。
この4本の配列の形は、2020年3月のコミット `87c37523`（「reactive refactor」）で入った。

## 本物はなぜ1000回登録していたのか

四歩目の話に戻る。

Solidは長いあいだ、読むたびに配列へ追加していた。
1000回読めば、`observers` にも `sources` にも1000個の要素が積まれた。
先の抜粋にある条件、`observers[observers.length - 1] !== Listener` は、2026年5月のコミット `fae8fbe3`（「Deduplicate repeated signal reads」）でようやく入り、solid-js 1.9.13に含まれている。
4本の配列が入ってから、6年と2か月後である。
同じコミットで、1000回読むエフェクトが1回だけ走ることを確かめるテストも足された（ミニ実装の同名のテストは、これを写したものだ）。

では `Set` にすればよかったのか。
そう単純でもない。
この条件は配列の末尾だけを見るので、コードから読む限り、別の計算がはさまって同じシグナルを読んだ場合は、重複が残る。
完全な重複排除にしなかった理由は、コミットにも変更記録にも書かれていない。
位置を覚える配列（`observerSlots` と `sourceSlots`）と両立させるには、配列のまま末尾を見るのが安上がりだったのだろう、と考えられるが、これは推測である。

つまり、ミニ実装の `Set` は「賢い」のではなく、依存を外す仕組みをまだ持っていないから気楽に使えているだけである。
4章でその仕組みを作るとき、この気楽さの請求書が届く。

ついでに言えば、読み取りで依存を記録する方式そのものも、Solidの発明ではない。
`signal.ts` の冒頭には、Adam Haile氏のリアクティブライブラリ**S.js**のライセンスが転記されている。
Solidは2019年5月のコミット `276dd32e`（「internalize reactive library」）まで、S.jsを外部依存として使っていた。

## 知覚されないシグナル

エピグラフのBerkeleyは、事物が存在するとは、それが知覚されることだと主張した。
同じ節で彼は書斎の机を例に出す。
部屋を出ても机が存在すると言えるのは、戻れば知覚できるか、ほかの誰かが知覚しているからだ、という。

シグナルの側から見ると、この主張はほとんどそのまま成り立つ。
誰にも読まれていないシグナルは `observers` が空で、書き込んでも何も起きない。
値は確かに書き換わっているが、それを確かめる方法は読むことしかなく、読めばその瞬間に知覚者として名簿に載る。
「戻れば知覚できる」机と同じで、シグナルの値は、読まれうるという意味でだけ存在している。

Berkeleyと違うのは、知覚の記録が片道だという点である。
読まれたシグナルは読み手を覚えるが、読み手が目を逸らしても（`if` の分岐が変わって、もう読まなくなっても）、名簿から消えない。
ミニ実装には、名簿から人を消す手段がそもそもない。
これも4章の宿題になる。

## 足りないもの

いまの `writeSignal` は、値を置き換えるとその場で名簿の全員を走らせる。
そのため、次の二つが起きる。

- **同じ値を書いても走る**：`setV(0)` を二度呼べば二度走る。値を比べていないからである。
- **書き込みをまとめる手段がない**：3回続けて書けば、3回走る。

どちらもテストで確かめている。
後者は本物のSolidでも、何もせずに3回書けば3回走る。

一つ目は比較を1行足せば直る。
二つ目はそうはいかない。
3回の書き込みを1回にまとめたいなら、「いまは走らせないで、あとで走らせる」必要がある。
では、その「あと」とはいつなのか。
それを誰が決めるのか。
次章では、書き込みをキューに積んでまとめて流す仕組みを足し、Solidの `writeSignal` と並べる。
